# Test262 conformance plan

How Jade runs [tc39/test262](https://github.com/tc39/test262) across **every** environment:
the to-bytecode pipeline (`jade-vm-frontend`), every interpreter, every JIT tier, every JS
tenant implementation, and the Rust-based autogenerated code (`jade-vm-core` dispatch,
`jade-primordial-rt`) — including the guest **globals** (the primordial realm) that bytecode
observes while it runs.

This is a plan, not a conformance claim. Jade's bytecode and frontend are deliberately a
subset (see "Ground rules" below); the plan's first job is to make that subset *measurable*
and every exclusion *loud and classified*, never a silent skip.

## Ground rules the architecture imposes

These are load-bearing constraints; every harness decision below follows from them.

1. **The frontend is a subset, and says so.** `jade-vm-frontend`
   (`crates/jade-vm-frontend/src/lib.rs`) lowers only constructs with a direct opcode in
   `packages/jade-data/index.ts`: no arithmetic (only the six comparisons), no exception
   handling, no parameter binding, no `undefined` literal. Anything else is
   `FrontendError::Unsupported` — an explicit, inspectable verdict. A test that fails to
   compile with `Unsupported` is a **skip-class**, not a failure; a test that compiles and
   then misbehaves is a **failure**.

2. **No host intrinsics, ever.** Guest globals come only from the tenant
   (`createPrimordialRealm` in `packages/jade-js/primordials/realm.ts`; generated Rust mirror
   in `jade-primordial-rt`). Test262's own harness files (`harness/assert.js`,
   `harness/sta.js`, `harness/propertyHelper.js`, …) are written in full JS and will *not*
   compile through the frontend subset. The harness must therefore be **hand-written against
   tenant operations**, exactly like the existing primordials — never compiled from
   test262's harness sources, never implemented via host `Reflect`/`Proxy` shortcuts.

3. **All tenant operations are generators.** Every interaction with a tenant — including
   running the harness's own assertions that touch guest objects — composes through
   `tenant.driveTenant` / `yield this.yieldTenant(...)`
   (`packages/jade-js/tenants/driver.ts`, `docs/tenant-generator-driver.md`). The runner is a
   driver consumer; it never calls `.next()` itself and never probes `.then`.

4. **JIT tiers share one per-op emission.** Tier 0/1 (`jade-vm-jit`, `reloop` feature) and
   Tier 2 (`jade-vm-jit-swc`) emit `op_await`/`op_yield`/`op_yieldstar` and the
   declared-variant/ambient-variant combination from the same code. Async/generator test262
   coverage exercises `addAsync`/`addGen`/`doubleGen`; the runner threads those flags at
   exactly the existing emission sites — it adds no new ones.

5. **Interpreter↔JIT parity is itself under test.** The same bytecode buffer runs through
   the TS interpreter and all JIT tiers. Divergence between environments is a bug **even if
   test262 would call it a pass**. The runner treats differential mismatch as its own failure
   class, independent of the test's verdict.

6. **`Id` hygiene in any SWC-touching tooling.** If the runner or manifest tooling inspects
   SWC ASTs, identifiers key compile-time bookkeeping by `Ident`, never flattened to
   `String` (see the global `AGENTS.md`).

## The environment matrix

Every row is a distinct conformance surface. "Tenant" columns list the JS tenant
implementations from `packages/jade-js` (`single_tenant`, `MultiTenant`, `MergedTenant`, a
`NarrowSpec`-validating wrapper from `narrow.ts`, a `hostToGuest`/`guestToHost` rewrite
wrapper from `rewrite.ts`); the Rust rows use `jade-tenant-rt` implementations instead.

| # | Environment | Executes | Tenants | Globals from | Where it runs |
|---|-------------|----------|---------|--------------|----------------|
| 1 | TS interpreter | `vm.ts` `runVirtualized{,A,G,AG}` (generated by `scripts/regen.ts`) | all JS tenants | `createPrimordialRealm` (TS) | Node |
| 2 | JIT Tier 0 | `jade-vm-jit` default emission, `new Function` | all JS tenants | TS primordials | Node |
| 3 | JIT Tier 1 | `jade-vm-jit` `reloop` feature | all JS tenants | TS primordials | Node |
| 4 | JIT Tier 2 | `jade-vm-jit-swc` (CFG round-trip, structured JS) | all JS tenants | TS primordials | Node |
| 5 | JIT tiers, real engines | tiers 0–2 via `js_sys::Function` | JS tenants | TS primordials | browsers via `wasm-pack test` (`crates/jade-vm-e2e-tests`, Chrome/Firefox/Safari) |
| 6 | WASM interpreter | `jade-vm-wasm` `run_virtualized{,_a,_g,_ag}` over generated `jade-vm-core::dispatch` | JS tenants (via wasm-bindgen) | TS primordials | Node (`wasm-bindgen-test`) and browsers |
| 7 | Native Rust interpreter | `jade-vm-core::exec_op` driven natively | `jade-tenant-rt` object-manager tenant | generated `jade-primordial-rt` | pure Rust, `cargo test` |
| 8 | WSDOM | Tier 0 via `jade-vm-wsdom` in a WSDOM-connected browser | WSDOM server tenant (`tenants/wsdom-runtime.ts`) | TS primordials | browser, remote — smoke shard only (transport latency) |

Row 7 is the "Rust-based autogenerated code" environment: both the dispatch it runs
(`jade-vm-core::dispatch`, generated by `scripts/gen/dispatch-rs.ts`) and its globals
(`jade-primordial-rt`, generated from the TS primordials by `jade-primordial-ir`) are
generated artifacts. Its expectations therefore double as a regression suite for the
generators themselves — a Rust/TS primordial divergence shows up here first.

Row 5 exists because each JIT tier's output is host-engine JS, and host engines differ
(Safari vs Chrome number/unicode edge cases). It runs a **fixed smoke shard**, not the full
matrix.

`ses_compat.ts` is a cross-cutting mode, not a row: any JS row may optionally run under SES
lockdown (`harden` present) to prove tenant isolation survives it.

## What "a test" means here

For each test262 test file, the runner produces one verdict per environment cell:

- `pass` — compiled, ran, assertions held (for `negative` tests: rejected with the right
  error at the right phase).
- `fail` — compiled, ran, and violated the test (wrong value, wrong property shape, harness
  `Test262Error`, unexpected throw).
- `differential-mismatch` — the test's verdict aside, this environment disagreed with the
  TS interpreter baseline on the same bytecode.
- `skip-unsupported-frontend` — `FrontendError::Unsupported`; records the exact message.
- `skip-parse` — `FrontendError::Parse`/TAC error on a non-`negative` test (parse-level
  negative tests *expect* this; see below).
- `skip-feature` — the capability manifest says this environment lacks the feature (e.g.
  `SharedArrayBuffer` without `includeSharedArrayBuffer`, any typed-array test without
  `BufferHooks`, `BigInt` arrays — deliberately unavailable, dynamic `Function`/`eval`).
- `skip-flag` — an environment-level flag mismatch: `module` (the frontend parses scripts
  only), `onlyStrict` until the frontend honors strict-mode semantics, `async` on a
  sync-only cell.
- `crash` / `timeout` — always failures; never silently retried away.

**No silent skips.** Every skip verdict carries its reason and is checked against the
capability manifest; a skip that no manifest entry or `Unsupported` message explains is a
runner bug and fails the run.

### Metadata handling

The runner parses each test's YAML frontmatter itself (vendored tiny YAML-subset parser on
the Rust side; a small dependency-free parser in TS) and honors:

- `negative: {phase: parse|early|runtime, type}` — `parse`/`early` map to
  `FrontendError::Parse`/TAC errors and are *passes* when compilation fails for the right
  reason. `runtime` negatives require exception semantics the bytecode doesn't have yet;
  they are `skip-unsupported-frontend` until exception opcodes land, at which point this
  whole class flips on at once.
- `flags`: `module`, `onlyStrict`, `raw`, `async`, `generated`, `non-deterministic`
  (excluded from the ratchet, still reported).
- `includes` — harness include files. **Not** compiled from test262 sources (ground rule 2);
  each include maps to a hand-written harness-primordial equivalent (below). A test naming
  an include with no primordial equivalent yet is `skip-feature` with the include named.
- `features` — cross-checked against the capability manifest.

## The Jade-native test262 harness (globals)

Installed into every realm under test, built the same way as
`packages/jade-js/primordials/*`: tenant-owned, allocated through tenant operations, guest
callbacks via `tenant.invoke` (TS) or the `jade-tenant-rt` traits (Rust).

- `Test262Error`, `$ERROR`, `assert` (+ `sameValue`, `notSameValue`, `compareArray`,
  `throws` once exceptions exist) — the `sta.js`/`assert.js` equivalents.
- `verifyProperty` / `propertyHelper` subset — property-descriptor assertions expressed
  through the primordial descriptor surface (`Object.getOwnPropertyDescriptor` /
  `Object.defineProperty`), which itself bottoms out in `tenant.{ownKeys,define,get}`; this
  is a primary consumer of the descriptor/exotic-trap surface (`Object.seal`/`freeze`
  included).
- `$DONE` — bound to the realm's `HostAsyncCapability`; presence is what makes
  `flags: [async]` runnable on async cells.
- `$262` object:
  - `$262.global` — the realm's own `globalThis` (a cheap, direct check that `GLOBAL` opcode
    and realm assembly agree).
  - `$262.createRealm()` — a fresh `createPrimordialRealm` on a fresh tenant. This is both a
    harness API and a genuine test of realm composability (and of `MergedTenant` bridging
    when the test requests it).
  - `$262.detachArrayBuffer` — only when `BufferHooks` were supplied; otherwise the tests
    needing it are `skip-feature`.
  - `$262.evalScript` — a host-side hook that runs `compile_to_bytecode` + the same
    execution environment on the same tenant. Deliberately **not** guest-`eval`: it never
    becomes an ambient intrinsic.
  - `$262.agent`, `$262.gc`, `IsHTMLDDA` — absent; dependent tests are `skip-feature`.
- `print` — routed to the runner log.

The global-object coverage tests (`test/built-ins/globalThis`, property enumerability of the
globals) run against the realm as assembled — the realm is the deliverable under test, so
the runner asserts the realm's own surface (no host global leakage) as its own test group.

## Repository layout

- `vendor/test262` — pinned git submodule of tc39/test262; the pin bumps only in dedicated
  PRs that re-baseline expectations in the same commit.
- `packages/jade-js/test262/` — TS runner, harness primordials, Node driver script,
  expectation files (`expectations/<environment>.json`, mapping test path → verdict class +
  optional issue link).
- `crates/jade-test262` — Rust runner library + binary: metadata parser, frontend compile
  oracle, JIT tier drivers, wasm glue, native-Rust cell (row 7), shared JSON report emitter.
  Expectation files are **shared** with the TS runner — one format, one ratchet.
- `docs/test262-plan.md` — this file. The capability manifest itself lives as data
  (`packages/jade-js/test262/manifest.json`) so the runner can check skips mechanically.

## The capability manifest

A single checked-in JSON mapping test262 `features` tags, harness includes, and bytecode
opcodes to per-environment support levels: `supported | unsupported | partial` + note. It is
**data-derived, not hand-guessed**: a manifest-refresh tool compiles every vendored test
through `jade-vm-frontend`, buckets by `Unsupported` message, and diffs the result against
the manifest. Rules:

- Adding an opcode to `packages/jade-data/index.ts` requires, in the same PR: `build.sh`
  (regen), a manifest refresh, and an expectation re-baseline showing the newly-runnable
  tests.
- A `partial` entry must name the missing sub-behavior (e.g. "`Promise` without subclassing
  support"); `partial` tests are expected-fail, not skip, so regressions and fixes both show
  up as diffs.
- The manifest is the single source of truth for skips; the runner refuses to emit a
  `skip-*` verdict the manifest doesn't justify.

## Differential core

For every compilable test, the runner executes the **same bytecode buffer** through the TS
interpreter first (baseline), then each JIT tier, then the wasm interpreter, asserting:

1. Same completion kind (return / throw / yield sequence).
2. `sameValue` on the completion value, compared structurally through tenant reads where the
   value is a guest object.
3. Same observable tenant-operation trace in a recording mode (a `Tenant` wrapper that logs
   the full `make`/`get`/`set`/`has`/`delete`/`ownKeys`/`define`/`assign` sequence) — this
   catches "right answer,
   wrong protocol" bugs that value equality hides, at the cost of being opt-in per shard
   (trace equality is stricter than conformance; tenant wrapper order differences that are
   semantically inert get an explicit allow-list in the manifest).

The `addAsync`/`addGen`/`doubleGen` matrix multiplies the async/generator shard: each such
test runs under every legal combination of declared variant × ambient flags, through
`driveTenant`, asserting THROUGH-tagging behavior for `doubleGen` exactly as the
`jade-vm-jit-swc` unit tests do.

## Phased rollout

Each phase ends on its completion criterion; do not start the next phase's tests until the
current phase's criterion holds on `main`.

**Phase 0 — infrastructure.** Vendor test262 at a pinned commit; land the metadata parser,
manifest skeleton, expectation format, runner skeletons, and the verdict taxonomy; prove the
pipeline end-to-end on one hand-picked literal test per Node cell.
*Done when:* `cargo run -p portal-solutions-jade-test262 -- --shard smoke` and the TS runner
both emit schema-valid JSON reports in which every non-`pass` verdict is manifest-justified.

**Phase 1 — TS interpreter baseline.** Hand-written harness primordials (`Test262Error`,
`assert` core, `$DONE`, `$262.global`); run the compilable subset on row 1 with
`MultiTenant`. Selected directories (the real test262 layout): `language/literals`,
`language/expressions/{equals,does-not-equals,less-than,less-than-or-equal,greater-than,
greater-than-or-equal}`, `language/statements/{if,block}`. (`built-ins/Object` waits for
Phase 4's `propertyHelper`.)
*Done when:* every compilable test in the selected directories has a stable verdict across
two consecutive runs, and the manifest's `unsupported` reasons match the runner's observed
`Unsupported` messages 1:1.

**Phase 2 — JIT parity in Node.** Rows 2–4 on the same subset, differential assertions on.
*Done when:* zero `differential-mismatch` verdicts on the Phase 1 subset across tiers 0/1/2,
and each tier's pass rate equals row 1's.

**Phase 3 — Rust-generated surfaces.** Rows 6–7: wasm interpreter in Node, then the
native-Rust cell with `jade-tenant-rt` + `jade-primordial-rt` globals.
*Done when:* the native-Rust cell's per-test verdicts match row 1's on the compilable subset
except where the manifest names a genuine Rust/TS primordial gap.

**Phase 4 — Globals and built-ins.** Grow realm coverage toward `built-ins/{Object,Function,
Reflect,Proxy,Promise}` and (with `BufferHooks`) `ArrayBuffer`/typed arrays; tenant-matrix
sweep (single/merged/narrow/rewrite wrappers) on the growing subset; SES mode on one row.
*Done when:* pass-rate deltas between tenant columns are explained one-for-one by manifest
entries, and `$262.createRealm` tests pass on every tenant column.

**Phase 5 — Async, generators, browsers.** `flags: [async]` shard through the driver;
browser row 5 smoke shard via `wasm-pack test --headless`; WSDOM smoke (row 8) optional.
*Done when:* the async/generator shard passes on all async-capable cells including
`doubleGen` combinations, and browser smoke matches Node verdicts on its shard.

**Ongoing — ratchet.** Expectations move `fail→pass` freely; `pass→fail` or a new
unexplained skip blocks the PR. Nightly full matrix; per-PR the Phase 1+2 subset.

## Reporting

One JSON report per run: `{ environment, tenant, tier, flags } → per-test verdicts`, plus
rollup pass rates per matrix cell and per manifest feature. A `test262-report` diff tool
compares two reports and prints only: newly passing, newly failing, newly skipped, and
verdict-class migrations. Coverage of the *frontend itself* (fraction of vendored tests that
compile) is reported as its own headline number — it is the metric that moves when bytecode
grows opcodes.

## Non-goals

- Full ECMAScript conformance. The subset is deliberate; this plan measures it, it does not
  close it.
- test262-fuzzer or fuzzing generally (separate effort).
- `module` goal support, strict-mode semantics, exception opcodes — each is its own
  frontend/bytecode plan; when one lands, this plan's manifest rules make the corresponding
  skip-classes flip in one re-baseline.
- Performance benchmarking of test262 execution.
